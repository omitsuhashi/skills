# 実装のための良いイシューの条件

## 対象と調査方法

調査基準日は **2026年10月26日（日本時間）**。人またはAIが既存ソフトウェアを変更するための、着手対象となるIssueを対象とする。アイデア受付、障害速報、探索課題、Epicには同じ完成度を要求しない。Issueは容器、ユーザーストーリーは要求の表現方法であり、両者を同一視しない。

2024〜2026年の一次研究を中心に、研究者の公開論文、学術出版社、arXiv、研究主体の技術報告を検索し、必要に応じて基礎文献を補った。検索群は user story quality / requirements quality / task description granularity / issue description underspecification / acceptance criteria / coding agents。下記14資料を主要な根拠集合として採用した。網羅的なsystematic reviewではなく、現時点の研究を使った焦点型の調査である。実験、観察研究、専門家評価、実務指針、プレプリントを区別する。

本ページは再利用可能な調査草案であり、このリポジトリのIssueテンプレート変更や運用ルールの採用を決定しない。既存Wikiの2ページを探索したが、本主題の直接の先行整理は確認できなかった。

## 結論と根拠の読み方

**良い実装Issueとは、実装者と評価者が「なぜ必要か・何を変えるか・どこまでか・何で完了を判定するか」を共有でき、重大な要求判断を勝手に補わずに進められる、まとまりのある変更単位である。** 以下は複数資料からの統合的な提案であり、単一研究がこの定義全体を検証したものではない。

特に注意すべき研究上の限界は次の通り。

- **形式的に整った文章と、実装成果は別である。** 2025年の8チーム・1,345ストーリーの観察研究では、測定した記述品質と開発効率の関係はほとんど検出されなかった。受入条件数と期限内完了には弱い関連があるが、増やせば速くなるという因果ではない。[S1]
- **短ければよいわけではない。** USeRの専門家評価では、極端に長いものと短いものが低評価となる傾向があった。ただし、これは専門家による記述評価であり、最適な文字数や工数を示すものではない。[S3]
- **万能の最適日数・story points・行数は、今回確認した研究からは決められない。** 記述の分解度、Issueの要求範囲、PRの差分量、作業時間は別の変数である。[S6][S8][S13]
- **技術情報の全面禁止も支持できない。** 2024年の産業事例では、解決策を指定する記述は理解・検証を妨げる場合と、見積・計画を助ける場合があった。2025年のaction researchでも、一律の記述ルールに実務者から反論が出ている。[S2][S4]

## 入っているべき情報

ここでいう「必要」は情報としての必要性であり、独立した見出しをすべてのIssueに設ける義務ではない。簡単な修正なら一つの短い説明にまとめてよい。既存契約・共通規約の安定したリンクで充足できる情報もある。

| 情報 | 着手時に答えられるべき問い | 適用と根拠 |
|---|---|---|
| 具体的なタイトル | 何の対象に、どの変化・問題があるか | 「改善する」だけで終わらせない。2026年のタイトルからの要件生成研究は具体性の重要性を示唆するが、実装成功の比較実験ではない。[S5] |
| 問題・目的・影響 | 誰の何が困るか。何のリスク・コストを減らすか | ユーザー価値に加え、保守性・運用・互換性も目的になる。要求の目的と実装案を混同しない。[S2][S7] |
| 現状と期待する状態 | 変更前後で、観測可能な振る舞いがどう違うか | 追加機能なら対象利用者・操作・結果、修正なら現象と期待との差を示す。[S5][S9] |
| 範囲と対象外 | 何を満たせば今回の変更は終わりか。近接した何は扱わないか | 独立した機能の混載、無制限な「関連箇所も改善」を避ける。対象外は誤解が起きるものを選ぶ。[S3][S7]からの適用提案 |
| 検証可能な受入条件 | 実装者以外も合否を判断できるか | 状況・入力・操作・期待結果を明らかにする。「コードを書く」「テストを足す」だけでは要求結果を示せない。[S1][S10] |
| 代表例と重要な境界 | 正常系、主要な失敗、境界で何が起きるか | 全組合せを列挙する必要はない。業務上の判断を分ける例を選ぶ。曖昧なルールは例との照合で確認する。[S10] |
| 守るべき制約 | どの契約・データ・権限・性能を守るか | 該当するときに明記。性能なら負荷条件・測定対象・閾値をセットにする。非機能要件を「速い・安全」で済ませない。[S2][S4] |
| 依存・前提と参照先 | 何が先に成立すべきか。どの仕様が正本か | 関連Issue、契約、設計判断への到達可能な参照。本文には判断に必要な要点を残す。[S7][S11] |
| 重大な未決事項と判断者 | 誰が何を決めるまで実装を進められないか | 事実・仮説・決定を区別する。要求を変える問いが残る場合は、実装着手可能と誤認させない。[S2][S4]からの適用提案 |
| 完了に必要な証拠 | 自動テスト、レビュー、実機、運用確認のどれが必要か | 必要な水準を示し、受入条件と対応づける。CI成功と統合された機能の完成を同一視しない。[S9][S13] |

優先度・担当・ラベル・見積は管理に有用だが、要求の意味が明確になることの代替ではない。見積は実装者が状況に応じて更新するものであり、story pointsの記載を良い要求の必須条件とはしない。[S6][S8]を踏まえた提案。

### 種類別に追加する情報

- **バグ修正:** 再現条件、最小の再現例、実際と期待の差。対象バージョン・環境、スタックトレースは現象に関係するものを記載する。再現不能なら頻度・観測ログ・未確認範囲を明示する。推定原因を確定事実として扱わない。開発者面談・調査でも再現情報と障害説明が重視される。[S14]
- **機能追加:** 利用シナリオ、入力と出力、許可と拒否の条件、既存動作との関係。
- **リファクタリング:** 保ちたい外部動作・公開契約、変える構造、改善の理由、回帰確認。無理に架空の利用者を作らない。[S4]
- **移行・運用変更:** 適用対象、既存データ・互換性の扱い、切替と復旧条件、完了を観測する方法。変更の危険度に応じて追加するという提案であり、全Issueに一律で求めない。
- **調査・探索:** 決めたい問い、調べる範囲、終了条件、残す証拠。実装結果を受入条件にするIssueとは分ける。未知の解消が実装範囲を変える場合に有効。

## 粒度はどれくらいがよいか

### 親の目的、受入可能な変更、実装の手順を分ける

| 単位 | 役割 | 実装Issueとの関係 |
|---|---|---|
| Epic・親Issue | 複数の変更にまたがる目的と全体の成功条件 | 大きくてもよい。子Issueの一覧だけで全体の受入確認を置き換えない |
| 着手する実装Issue | 一つの主目的に向かう、受入判定できる変更 | 本調査の対象。必要な層を横断してもよい |
| タスク・チェックリスト | 調査、編集、テストなど、変更を実現する作業 | 受入条件と区別。作業一つごとにIssueを作る必要はない |

Scrum Guideは、Sprint Planningで選ぶProduct Backlog Itemが一つのSprint内でDoneにできることを示す。一方「1日以下」は、その項目を実現するための作業への分解についての説明である。**全Issueを1日以下にするルールではない。** これはScrumの運用指針であり、科学的な最適値ではない。[S8]

実務上の初期目安としては、**レビュー・検証も含め数日で完了を確かめられる変更**を仮置きし、実績に応じて調整することを提案する。チームやシステムによらず有効な日数として研究が確定した値ではない。数時間で閉じる修正も、不可分な移行もあり得る。

### 分割を検討するサイン

以下はQUS、INVEST、粒度実験、近年のAI研究を実装Issueへ適用した判断基準。[S6][S7][S11][S13]

1. **別々に受け入れられる成果が複数ある。** 一方を延期しても他方が有用なら分ける候補。
2. **主要な振る舞いと、ついでの改善が混ざっている。** 同時に行う必要性を説明できなければ切り離す。
3. **一部はすぐ実装でき、一部は要求・技術上の重大な判断待ち。** 後者を探索として切り出す。
4. **変更ごとに依存先、責任者、リリース条件が大きく違う。** 調整待ちを含む巨大な一件になっている。
5. **差分と受入条件を一度に説明・レビュー・検証できない。** 行数だけでなく理解の負荷を確認する。

ただし、単純な細分化にも限界がある。

- 同じ不変条件を守るため不可分な変更は、別Issueにしても実質的な独立性がない。
- UI / API / DBという層だけで分けると、各Issueが利用可能な変化を持たないことがある。機能Issueなら、一つの操作・対象・利用条件を端から端まで通す分割をまず検討する。[S11]
- 基盤・保守・セキュリティ変更は、直接のUIを持つ必要はない。契約や不変条件の達成を独立して検証できればよい。
- IssueとPRは異なる管理単位である。一件一PRは便利な場合があるが、移行・互換性維持では複数PRもあり得る。対応関係と最終受入を失わないことを優先する。
- 小さな変更に重い要件定義会議を一律に要求しない。Example Mappingの2社事例では、1〜2時間程度の小さなストーリーに30分の会議を行う費用が問題になり、関連項目をまとめて議論する方法が提案された。[S10]

### 粒度の具体例（本調査からの提案）

「エクスポート機能を改善する」は、目的と終点が不明である。一方「UIを作る」「APIを作る」「DBを変える」の分割だけでは、利用できる結果が残らない可能性がある。

たとえば親を「必要な明細を取り出せるようにする」とし、実装Issueを「権限のある利用者が、指定期間の明細をCSVで取得できる」に絞る。項目・文字コード・期間境界・権限・失敗時の振る舞いを受入条件にし、定期配信や他形式は別の成果として検討する。CSV成功とアクセス制御は、同じ契約の安全性に必要なら切り離さない。実装手順はこのIssueのチェックリストで扱える。

## 入れない方がよい情報・書き方

### 通常は削る、または分離する

| 避けたいもの | 問題 | 代わりにすること |
|---|---|---|
| 無関係な機能、ついでの整理、将来全部の要望 | 一つの変更の終点が消える | 別Issue・親の候補へ分離 |
| 根拠のない実装方法の固定 | 要求を満たす選択肢を不必要に狭める | 必須制約と参考案を区別し、理由を添える |
| 曖昧な形容詞だけの要求 | 「高速・適切・直感的」の合否が一致しない | 利用条件・観測結果・具体例を記載 |
| 作業手順だけのチェックリスト | 作業は終わっても要求を満たしたか分からない | 結果の受入条件を別に記載 |
| 会話ログ、古い案、撤回済み決定の無整理な貼付 | 現在の要求と履歴が競合する | 本文に現在の合意、履歴はリンクと短い理由 |
| 他文書と重複する長い仕様コピー | 更新時に食い違う | 正本リンクと今回適用する範囲・要点 |
| 外部リンクや動画「だけ」の説明 | 閲覧不能・リンク切れで要求が失われる | 重要な事実・期待結果は本文にも残す |
| 秘密情報・個人情報を含む生ログ | 要求に不要な情報まで露出する | 最小化・マスクした再現資料 |
| 説明にない合否基準や、不要な内部実装名を強制するテスト | 正しい別実装を不当に不合格にする | テストと公開された要求・契約を整合させる |

上表の最小化・境界・解決策に関する根拠は[S2][S4][S7]、曖昧さは[S5]、テストとの不整合は[S9]。履歴整理・正本管理・機密最小化は、これらを運用へ適用した提案であり、各行の効果を比較実験で検証したものではない。

### 一律に「入れるな」としてはいけないもの

- **技術設計・変更候補ファイル:** 既存契約、セキュリティ上の制約、決定済みの設計、再現の手がかりなら有用。「この方法が必須」と「調査候補」を区別する。正確なパスの網羅を全Issueの義務にはしない。[S2][S4]
- **非機能要件:** 性能・権限・信頼性・互換性は短くするために落とさない。実務者が必要性を示している。[S4]
- **背景や理由:** QUSのMinimalはユーザーストーリーの短文部分に関する規則。Issue全体から背景・受入条件・添付資料を消す根拠にはならない。[S7]
- **未決事項:** 消すと推測を誘う。実装を止める問いか、実装者が決めてよい問いかを分けて残す。
- **技術作業Issue:** バグ修正や保守を「As a user…」形式に無理に変換しない。形式を外しても、目的と受入は明確にできる。[S4]

## AIに実装を依頼するときに重くなる条件

人にとっても必要な条件だが、共有された暗黙知を期待できない場合には次を明示する。

1. ドメイン用語と判断規則。特に金額・権限・データ保持・互換性をAIの推測で埋めさせない。
2. リポジトリ内の契約・指針・テストへの入口。全ファイルの説明をIssueへ複製する必要はない。
3. 観測可能な受入条件と、必要な統合確認。部品を生成しただけで全体が動いたと判断しない。
4. 未決事項の相談先と、実装者に任せる裁量。候補案を必須要求へ勝手に昇格させない。

WiseSpec（ASE 2026 SRC）は、要求を構造化・評価・改善する枠組みを3ベンチマーク各100件、2モデルで評価している。ただし要求改善だけを切り出す比較ではなく、生成したコードとテストによる代理評価も含むため、「人がIssue欄を増やせば同じ改善率になる」とは言えない。[S12]

2026年10月19日公開のPACEプレプリントは、43企業タスク・750受入点を扱い、不完全な実装と統合漏れを主要な問題として報告する。タスクサイズ関連の4指標は性能との相関の信頼区間がいずれも0を含み、暗黙要件比率との探索的な関連も多重比較補正後は強い断定ができない。**Issueを短くすれば解ける、という結論には使えない。** 新しい補助根拠として扱う。[S13]

## 書式より先に確認する着手条件

以下は研究から導いた軽量なレビュー質問であり、検証済みの採点尺度ではない。

- 実装者が「何が変わるか」を具体的に言い直せるか。
- 評価者が受入条件から合否の例を作れるか。
- 変更範囲と、重要な対象外について認識が一致しているか。
- 既存のデータ・権限・契約を壊さない条件が把握されているか。
- 実装方針を変える重大な未決事項が解消されているか、判断手順が明示されているか。
- 必要な資料にアクセスでき、現在の要求と過去の議論を区別できるか。
- レビュー・検証まで含む一つの変更として扱えるか。

満たせない場合でも、受付Issueとして不適切とは限らない。要求の精緻化や探索が必要な状態として扱う。全件に重いDefinition of Readyを追加するという提案ではない。

運用後の有効性は、欄の充足率だけでなく、要求の誤解による手戻り、実装中の追加確認、受入時の争点、再オープン、レビュー・検証を含む完了時間で点検する。追加確認が増えても、早期に問題を発見した結果かもしれない。チーム・Issue種別・複雑さを分けて解釈し、Issue件数を増やすことを目標にしない。[S1][S2][S10]を踏まえた運用提案。

## 主要資料と限界

### S1 — 実務上の効率との関係（2025、RE）

Molenaar & Dalpiaz, [The Impact of Requirements Artifacts on Efficiency in Agile Development: A Case Study](https://webspace.science.uu.nl/~dalpi001/papers/mole-dalp-25-re.pdf)。1組織・8チーム・19 Sprint、1,345ストーリーと面談。記述品質はQUSの4基準で測定。受入条件数と期限内完了の相関は全体ρ=.128、有意なのは8チーム中3チーム。観察研究で交絡や一般化に限界があり、品質が無意味だという証明でもない。

### S2 — 品質は後続活動と文脈で変わる（2024、REFSQ）

Frattini, [Identifying relevant Factors of Requirements Quality: an industrial Case Study](https://arxiv.org/html/2402.00594v1)。Ericssonの面談とIssue記録から17因子・11相互作用を整理。要求の欠落の実害と、解決策指向の利害両面を示す。単一事例であり、規範的な品質チェックの多くに実害の実証が不足しているとも指摘する。

### S3 — USeR（2025、公開論文）

Hallmann et al., [USeR: A Web-based User Story eReviewer for Assisted Quality Optimizations](https://arxiv.org/html/2503.02049v1)。77候補指標を34へ整理、8指標を実装。自動車・医療の2プロジェクト、100ストーリー・4専門家で評価。構造、明瞭さ、簡潔さなどの観点を提供するが、実装の速度・正確性を測った研究ではない。Small指標も専門家評価と期待通りの関係にならず、形式得点の限界を示す。

### S4 — 一律の書き方への反証（2025、PROFES）

Molenaar & Dalpiaz, [Improving the Writing Quality of User Stories: A Canonical Action Research Study](https://webspace.science.uu.nl/~dalpi001/papers/mole-dalp-25-profes.pdf)。4チームに指針を導入し、その後の記述と面談を分析。Atomic違反は減少した一方、Minimal改善は持続しなかった。実務者は技術情報や保守・非機能要件の必要性を説明し、著者も指針を改訂。一律の全面禁止を支えず、実装成果の因果評価でもない。

### S5 — タイトルからの要件生成（2026-05-26、Requirements Engineering）

Paiva et al., [From issue titles to requirements: an empirical study of large language models and prompt engineering strategies](https://link.springer.com/article/10.1007/s00766-026-00462-z)。5 OSSの150タイトル、2モデル×3プロンプトで900要求を生成、LLM評価を50要求・5人で部分検証。明確さ・検証可能性・単一性にトレードオフ。測定対象は文の内在的品質で、ドメイン上の正しさ・要求全体の完全性・実装成果は保証しない。

### S6 — 記述の分解度の実験（2019公開受理稿、IEEE TSE）

Karac, Turhan & Juristo, [A Controlled Experiment with Novice Developers on the Impact of Task Description Granularity on Software Quality in Test-Driven Development](https://oulurepo.oulu.fi/bitstream/handle/10024/28378/nbnfi-fe202001081509.pdf?sequence=1)。48大学院生のクロスオーバー実験。細かなサブタスク記述で機能的な正確性・完全性が改善。初心者・TDD・短時間課題での結果であり、Issue分割の最適日数を示さない。

### S7 — QUS（2016、Requirements Engineering）

Lucassen et al., [Improving agile requirements: the Quality User Story framework and tool](https://link.springer.com/article/10.1007/s00766-016-0250-x)。構文・意味・実用の13基準と検出ツール、18社・1,023ストーリーで評価。Atomic、Minimal、Problem-oriented、Unambiguous、Conceptually sound、Conflict-free、依存の明示等を提供。主な評価は品質欠陥の検出性能であり、実装成果を直接保証する基準ではない。

### S8 — Scrum Guide（2020、原著者による指針）

Schwaber & Sutherland, [The Scrum Guide](https://scrumguides.org/scrum-guide.html)。Product Backlog Itemと実現作業の単位、継続的なrefinement、Definition of Doneの役割を区別する。実験研究ではなく、Scrumの規範的な説明。

### S9 — 説明と評価条件の不整合（2026-02-23、研究主体の技術監査）

OpenAI, [Why SWE-bench Verified no longer measures frontier coding capabilities](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)。失敗しやすい138課題を選んで専門家監査。35.5%に不要な特定実装を強制する狭いテスト、18.8%に説明外の機能を要求する広いテストを報告。選択された失敗群なので全500課題や一般のIssueの欠陥率に外挿できない。ここではテストと要求の一致が必要な根拠として利用。

### S10 — 例を使う要求の精緻化（2021、RE）

Berends & Dalpiaz, [Refining User Stories via Example Mapping: An Empirical Investigation](https://webspace.science.uu.nl/~dalpi001/papers/bere-dalp-2021-re.pdf)。2社・13回のExample Mapping事例から共有理解への寄与と適用条件を調査。小さいストーリーでの会議費用に注意が必要。主な評価は質問票・事例で、長期的な実装成果の因果は未検証。

### S11 — INVEST（2003、原提唱者による実務指針）

Bill Wake, [INVEST in Good Stories, and SMART Tasks](https://xp123.com/invest-in-good-stories-and-smart-tasks/)。Independent / Negotiable / Valuable / Estimable / Small / Testable、層を横断する分割、ストーリーとタスクの区別を提案。覚えやすいチェック観点であり、科学的に確定した閾値やチェックリスト充足による成功保証ではない。

### S12 — WiseSpec（2026-09公開、ASE 2026 SRC）

Tian, [WiseSpec: Requirements-Driven Agents for Code Generation](https://arxiv.org/html/2609.00568v1)。3ベンチマーク各100件・2モデルで要求生成・評価・改善の枠組みを比較。要求を固定入力とみなさない研究の例。短報で、実行による代理評価の妥当性、要求以外の改善要因、ベンチマーク偏りに留意する。

### S13 — PACE（2026-10-19、プレプリント）

Liu et al., [When Coding Agents Outpace Review: Evaluating PRD-Driven Development in Mature Enterprise Repositories](https://arxiv.org/html/2610.26394v1)。43企業タスク・750受入点を使い、単体的なコード生成と業務・統合要求の充足を区別。原PRD・コード等にアクセス制限があり、評価は参照変更を使って構成される。査読結果・外部再現を確認しておらず、普遍的なIssue条件の確証にはしない。

### S14 — バグ報告の情報要素（2020、Empirical Software Engineering）

Soltani et al., [The significance of bug report elements](https://link.springer.com/article/10.1007/s10664-020-09882-z)。35開発者への面談、305人への調査、250の人気GitHubプロジェクト分析。障害説明、再現手順またはテストケース、スタックトレースが重視された。修正案などは相対的に低い重要度。実際の解決時間との分析は観察研究であり、全Issueの必須欄やテンプレートの因果効果へは一般化しない。
