# 実装Issueの点検とインタビュー

実装者と評価者が、なぜ必要か・何を変えるか・どこまでか・何で完了を判定するかを共有できるIssueにする。見出しの充足率や文章量ではなく、要求を勝手に補わず着手・受入できるかを判定する。受付段階のアイデアや親Issueに、実装着手時と同じ詳細度を要求しない。

## 内容と粒度を判定する

既存Issueでは現在の本文・関連する決定を読み、利用できるリポジトリの契約・テンプレート・参照資料と照合する。会話で既に決まったことを優先し、事実、仮説、参考案、必須条件を区別する。取得できない資料の内容は推測しない。

| 観点 | 十分と判断できる状態 |
| --- | --- |
| 目的と変更 | タイトルと本文から、対象・現状の問題・期待する結果・必要な理由が分かる |
| 範囲 | 今回の成果と、誤解されやすい対象外が分かる |
| 受入 | 実装者以外も合否を判定できる。代表例と重要な失敗・境界の期待が分かる |
| 制約 | 関係するデータ、権限、互換性、性能等の条件が具体的。既存契約で充足するものは参照できる |
| 前提と未決 | 依存先、正本、重大な未決事項と判断者が分かる |
| 完了の証拠 | 必要なテスト・レビュー・実機や統合確認が受入条件に対応する |
| 粒度 | 一つの主目的に向かい、レビュー・検証まで含め一つの変更として受け入れられる |

項目は情報として確認し、全Issueに同じ見出しや条件を追加しない。バグなら再現条件・実際と期待の差、機能なら利用シナリオと入出力、保守なら改善理由と維持する契約、移行なら既存データ・切替・復旧の条件を必要な範囲で補う。管理用のラベルや見積だけで要求の十分さを判定しない。

粒度は日数・story points・行数の一律閾値で決めない。別々に受入・延期できる成果の混在、独立したついでの改善、重大な探索待ち、異なる依存先やリリース条件、レビュー・検証の難しさがあれば分割を検討する。親の全体目的、受入可能な実装Issue、内部の作業タスクを分け、UI/API/DBの層や一作業ごとに機械的にIssue化しない。不可分な不変条件を保つ変更はまとめる。複数Issueへ分ける場合は、各成果・依存・全体の受入を失わない分割案を示す。

不要情報も点検する。無関係な要望、根拠のない方法の固定、曖昧な形容詞、現在の要求と競合する古い議論、仕様の重複コピーは整理する。作業手順だけなら結果の受入条件を補い、外部リンクだけなら必要な要点を本文へ残す。必要な背景・非機能要件・決定済み設計は保持し、技術情報を全面禁止したり、保守Issueを無理にユーザーストーリー形式にしたりしない。説明にない機能や不要な内部実装を受入テストで強制しない。

まず「実装に着手できる」「精緻化が必要」「探索・意思決定が先」の判定と、その理由を短く返す。粒度の変更が必要なら併記し、足りない情報・整理する情報・分割候補と、解消に必要な行動を対応づける。読取だけの点検依頼なら、判定と修正案までに留める。

## 不足を聞き、本文を更新する

重要な不足がある場合はチェック結果だけで終えず、判断を変える質問からインタビューする。既存資料から確認できることは先に調べ、ユーザーにしか決められない要求・優先順位・許容範囲を質問する。一度に答えやすい少数へ絞り、質問の理由と、選択によって何が変わるかを示す。妥当な選択肢があれば提案するが、仮の数値や案を合意済みとして扱わない。

例えば「高速に出力」なら、対象データ量と、どの操作のどの応答時間を受け入れるかを確認する。担当者が判断できなければ、測定すべき条件や決定者を整理する。要求を決めるための調査を、要求が確定した実装として進めない。

回答のたびに、確定した内容を依頼された本文へ反映し、残る不足と粒度を再判定する。未回答に依存しない整理も進め、同じ質問を繰り返さない。未決が残ればその内容・判断者・必要な調査を明示し、勝手に受入条件を補完しない。ユーザーが中断・回答保留を選んだ場合は、そこまでの本文と残る判断を渡す。

本文は現時点の要求の正本として整え、質問回答ログをそのまま積み上げない。既存の必要な要求、決定の理由、参照は保持する。不要な記述の整理と要求そのものの取り下げを区別し、要求の削除・範囲変更に合意が必要なら、その判断をインタビューで確認する。既存書式を使い、必要情報を過不足なく表現できれば新しいテンプレートを強制しない。

## 依頼範囲へ反映し、結果を確認する

本文の作成・更新依頼は、その対象の編集として扱う。読取のみ、草案のみという指定を守り、スキルの呼出しやインタビューへの回答だけで外部更新の権限が増えたとは扱わない。既に作成・更新を依頼されていれば、回答を反映するたびに同じ許可を取り直さない。複数Issueへの分割案から新しいIssueを作る操作は、依頼範囲に含まれる場合だけ行う。

書込先は対象リポジトリの指示に従う。外部Issueの更新前には最新本文を確認し、他者の変更を失わないよう統合する。実際に反映したら再取得して確認し、作成・更新した参照先と変更点を示す。能力・権限不足や更新失敗なら、更新後の草案と未反映の理由を渡し、成功したと報告しない。作成の成否が不明なまま同じIssueを再作成しない。

完了は、重大な不足が解消されて受入可能な変更単位になったか、残る未決事項と次に必要な行動が明示され、依頼範囲の本文更新が確認できたとき。未決を残す場合は「精緻化が必要」「探索・意思決定が先」として渡す。Issueを整えたことを実装・テスト・リリースの完了とは報告しない。

## 基準の根拠と限界

必要情報・粒度は研究からの適用指針であり、検証済みの採点尺度や固定の必須欄ではない。通常の利用で資料の再読は不要だが、基準の妥当性を見直すときは原典を参照する。

- [Molenaar & Dalpiaz, RE 2025](https://webspace.science.uu.nl/~dalpi001/papers/mole-dalp-25-re.pdf): 8チーム・1,345ストーリーで形式的品質と効率の関係は限定的。受入条件数との関連も因果ではない。
- [Molenaar & Dalpiaz, PROFES 2025](https://webspace.science.uu.nl/~dalpi001/papers/mole-dalp-25-profes.pdf): 一律の記述指針に対して、実務者が技術情報・保守・非機能要件の必要性を説明。
- [QUS, 2016](https://link.springer.com/article/10.1007/s00766-016-0250-x): 単一性・曖昧さ・整合・依存等の点検基準。短文のMinimalをIssue全体の情報削除へ広げない。
- [Karac et al., IEEE TSE](https://oulurepo.oulu.fi/bitstream/handle/10024/28378/nbnfi-fe202001081509.pdf?sequence=1): 初心者のTDD実験で細かなタスク記述が品質を改善。普遍的なIssueサイズは示さない。
