# 複数Issueの成果と到達点

複数Issueで一つの成果を作るとき、全体で何ができるようになるか、いつ、どのIssueが必要か、何を並列・直列で進められるかを結ぶ。既存の親Issueや全体計画を再利用し、個別Issueの集合だけでは読めない関係を補う。

## 到達点から必要なIssueを選ぶ

全体の目的から、利用者が何をできるかでマイルストーンを置く。「API実装完了」等の作業名だけで済ませず、到達を観測できる条件・証拠を対応させる。調査・設計なら、根拠を伴って何の判断を下せるかを成果にする。

| 単位 | 保持する情報 |
| --- | --- |
| 親Issue／全体計画 | 誰の何を実現するか、全体の受入、マイルストーン一覧、必要なIssueと順序、重大な未決事項 |
| マイルストーン | 到達状態、受入条件と証拠、時点、必須Issue。後回しにできるIssueは区別する |
| 個別Issue | 今回の変更と理由、受入条件、直接の前提、親・該当マイルストーンへの参照、個別の重要な制約・未決事項 |

到達点から逆に必要な成果を洗い出し、既存Issueへ対応づける。成果の欠落・重複・全体目的に結びつかないIssueを点検する。別々に受入・延期できる成果で分け、全体の仕様を各子へコピーしない。個別の内容・粒度・簡潔さは [実装Issueの点検](implementation-issues.md) に従う。

「実装済み」「統合検証済み」「公開・運用可能」は必要に応じて分ける。必須Issueが全て閉じていても、到達点の統合・利用・運用の受入が未確認なら、達成済みとしない。

## 到達時点と未定を区別する

合意した期日、根拠付きの見込み、前提成立後の相対時点を区別する。未指定の暦日・工数・担当人数を補わない。日付が不明でも、どの前提と検証の後に利用可能になるかは整理する。

日付が判断に必要なら、未定の内容と、誰の何の判断・調査が必要かを示して重要点だけ確認する。相対時点を示すことと、納期が決まることは別である。既に与えられた期日は保持し、実現可能性が不明なら必要な根拠を残す。

## 依存・並列・合流を示す

Aの成果・契約・判断がないとBの着手や受入が成立しない場合に `A → B` と理由を示す。着手の前提と、統合・公開の前提を区別する。単なる関連リンクや担当者の一致から依存を断定しない。前提が未確認なら、その関係も未確認とする。

独立する仕事は並列可能とし、合流後の統合確認を明示する。共有ファイル・環境の競合や人員不足による実行順は、成果そのものの依存と分ける。並列可能という計画は、人数の確保や並列実行の許可を意味しない。

循環や不足した前提があれば、影響する部分を着手可能とせず、契約の先行合意、粒度の見直し、探索・意思決定へ戻す案を示す。前提・範囲・期日が変わったら、影響する到達点・順序と検証根拠を点検し直す。

小規模なら表と矢印で十分。次は説明用の仮例で、必須書式ではない。

| 到達点 | できること／確認 | 時点 | 必須Issue |
| --- | --- | --- | --- |
| M1 | 隔離環境でプレビューを試せる。統合シナリオで確認 | A・B・Cと統合確認の後。暦日は未定 | A: 入出力契約、B: 生成処理、C: 画面 |
| M2 | 本番利用でき、監視・復旧手順も確認できる | M1受入と公開判断の後。期日は未定 | D: 公開準備・運用検証 |

Aの契約をB・Cの両方が必要とする例なら、`A → (B ∥ C) → M1の統合受入 → D → M2の運用受入`。契約を基にB・Cの実装は並列可能だが、公開操作の許可は別に確認する。

## 計画を反映して確認する

対象の管理基盤に親子・マイルストーン・依存の機能があれば既存運用に合わせる。機能や権限がなければ本文の表・参照で関係を保持し、管理画面への未反映を示す。特定のサービスやProjectを必須にせず、情報ごとの正本を定めて各Issueへの重複を減らす。

完了時には成果・到達点の受入と時点・必須Issue・依存と合流が対応し、重大な未決事項と次に必要な判断が分かることを確認する。未決が残る部分は精緻化・探索待ちと区別する。実際の作成・更新と再取得は [実装Issueの反映手順](implementation-issues.md#依頼範囲へ反映し結果を確認する) に従い、依頼範囲で行う。計画の作成を実装・公開の完了とは扱わない。
