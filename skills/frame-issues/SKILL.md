# よいイシューを設定する

答えることで重要な判断や次の行動が変わる問いを選ぶ。「イシュー」は思考上の論点であり、GitHub等の作業票とは区別する。

## 入力・出力・必要な能力

- 入力: 話し言葉の未整理な課題・悩み、または点検したいイシュー。達成したい結果、事実、対象・期限・資源・指定済みの選択は、提供された範囲で使う。
- 出力: 相談には暫定のイシュー案と選ぶ理由、点検には妥当性の判定と根拠・必要な修正。依頼に応じて、答えを分ける証拠と結果を使う判断・次の一手まで具体化する。未確定事項はそのまま示す。
- 必要な能力: 提供された文章の読解と問いの構成。重要な不足を解消する対話や、根拠の調査は必要な場合だけ行う。外部資料・ファイルを扱う場合は利用可能な読取・検索能力を確認し、取得できなければ提供情報で作れる暫定案と不足を示す。特定のツールや他のスキルは必須にしない。

## 相談の種類に合わせて返す

- 課題や悩みからの提案: 話の順序や整理の度合いを問わず、得られた材料で「こういうイシューとして考えるのはどうでしょう」と暫定案と理由を短く返す。異なる切り口が判断に効く場合は候補を添える。問いの選び方を変える不足だけ確認し、ユーザーの回答や修正を踏まえて磨く。詳細な分析計画は、求められた段階で具体化する。
- 提示されたイシューの点検: 「妥当」「修正が必要」「情報不足で判断保留」などの判定と理由を先に返す。妥当な部分を残し、修正が必要なら弱い点に対応する最小限の改善案を示す。情報不足なら、何が分かれば判定できるかを示す。問いの妥当性と、問いへの答えが既に判明しているかは分けて判断する。

## 依頼の背景をつかむ

依頼を言い換える前に、何が起き、何が困り、何を達成したいのかを区別する。依頼者の評価・観察した事実・原因の推測を分け、根拠と対象期間・場面を確認する。「うまくなりたい」という願望だけで、現在下手という事実を認定しない。

「売上を上げたい」なら、購入者・単価・頻度などのどこで変化が起きたかと、利益計画などへの影響を見る。原因側への掘り下げと、目的・影響側への視点変更を併用する。原因が未確定なら、それを確かめる問いを先に置く。

ユーザーが指定した製品・手段・作業範囲を前提として保持する。別の問いなら成果が改善しそうな場合は、その理由を示す提案として扱い、依頼を勝手に別の仕事へ置き換えない。明確な定型作業なら、その作業を実行する流れへ戻る。

不足情報は、中心の問いや判断を変えるものだけ確認する。既に提供された情報は聞き直さない。回答待ちでも確定できる部分は進め、未回答に依存する選定や結論は暫定とする。

## 候補を出し、今解く問いを選ぶ

事実と影響のそれぞれから、原因を確かめる問い、選択を決める問い、選んだ手段を具体化する問いを必要な範囲で出す。まだ対象を選んでいない段階で、広告や機器購入などの手段へ固定しない。

候補を出す段階では早く一つに絞りすぎず、選ぶ段階では目的への寄与・緊急性・使える資源を比べる。根拠のない効果量や順位を作る代わりに、選定理由と不確実性を示す。原因への対応と残る影響への備えが両方必要なら、別の問いとして順序や関係を示す。

| 点検すること | 弱い問いの兆候 | 改善する方向 |
| --- | --- | --- |
| 判断の対象 | 「今後どうする？」だけで調べる方向がない | 確かめる仮説、比較する選択肢、決める範囲を置く |
| 答える価値 | 「ブランド力を上げるべきか？」など既知の肯定で終わる | どの答えなら判断・行動が変わるかを示す |
| 事実との接続 | 指示の裏返しや、根拠のない原因・手段への固定 | 実際の現象と影響へ戻り、推測を検証対象にする |
| 優先する理由 | 抽象的な案出しのまま、すべてを同時に扱う | 今取り組む理由を目的と資源に結びつける |
| 答えへの道筋 | 何を見れば答えと言えるか分からない | 対象・期間・証拠と、今回判断できる範囲を決める |

スタンスは暫定仮説として置き、別の可能性と反証を残す。探索中なら既存の材料から仮説を作り、材料が足りなければ観察する問いを置く。結論を先に決めて証拠を探す手順にしない。

常識への反対や奇抜さを価値にせず、未解決で判断に効く違いを探す。結論が常識どおりでもよい。疑問文やYes / Noの形式自体を品質基準にせず、具体的な「どうすれば？」も対象と判断への接続があれば使える。

例えば「売上を上げるべきか？」を、「今期の利益計画の未達に対し、顧客回復と費用削減のどちらへ先に資源を配分すべきか？」へ変えられる。ただし利益が目的で、その選択が許されていると確認できた場合の例である。売上が必須の目標なら、その制約の中で問いを選ぶ。

## 証拠と次の行動へつなぐ

仮説や選択肢を分けるために必要な情報を選ぶ。現場の記録・観察・利用者の発言など、元の情報へ戻れる根拠を優先する。一次情報も記憶・立場・聞き方の影響を受けるため、発言と事実・因果の解釈を分ける。分解だけで原因を確定しない。

情報が増えるだけで判断が進まなくなったら、問いを一文に戻して次に必要な証拠を絞る。すでにある材料で今回の判断ができるなら、追加収集を終了する。仮説を確かめられない場合は、足りない証拠と、より小さく答えられる問いを示す。

詳しく整理する段階では、答えによって誰が何を決めるか、次に何をするかを明示する。以下はその際の参考項目として、必要なものだけを使い、ユーザーの指定形式へ合わせる。

```text
今答える問い:
選ぶ理由・達成したい結果:
事実・根拠／暫定仮説・別の可能性:
必要な証拠・答えと判断する条件:
答えによって変わる判断・次の一手:
未確定事項・問いを見直す条件:
```

提案の初回応答は、暫定の問いと選ぶ理由、必要なら次に確認する重要点を示せたら完了。点検は、判定と根拠、必要な修正または不足を示せたら完了。詳しい論点設定では、問い・選定理由・必要な証拠・結果の使い道が対応し、回答できる範囲と不足を示す。原因や目的が未確定なら、確定した問いとして扱わず暫定案を渡す。実際の調査・意思決定・施策の成果まで達成したとは報告しない。

後続の調査・分析・資料作成も依頼されている場合は、選んだ問いを短く記し、各作業がその答えを進めるかを確認しながら続ける。新事実で前提が崩れたら、問いを保つことより、その根拠を見直すことを優先する。見直しの頻度は作業に合わせ、週次などの固定ルールを加えない。

問いの整理と、Issue登録・購入・システム変更などの実行は別の操作として扱う。このスキルの利用だけでは後続操作の権限は増えない。
