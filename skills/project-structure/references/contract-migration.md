# 文書から所有機能への契約のコード移管

文書にある実装用の型・interfaceをコードへ移す場合に読む。目的は、実装とアダプターが同じ契約を参照でき、通常の型検査に含まれること。業務仕様の確定やユースケースの実装は依頼範囲に含まれる場合だけ行う。

## 移管する契約を決める

- 対象のユースケース・資料と契約の所有機能を明記する。範囲が未指定なら既存設計から一つの完結した責務を選ぶ。選択が業務仕様を変える場合は、その未決事項を確認する。
- 対象資料のコードブロックと本文中の型定義を検索し、呼び出し元・既存コード・schema・公開窓口と照合する。現行契約、比較用の擬似コード、未採用案、過去レビューを区別する。未決の業務条件は補完せず、移管できる範囲と保留を明示する。
- 既存のコード定義を優先し、別定義を増やさない。文書とコードが食い違う場合は正本と採用経緯を確認する。未取り込みのPRは参照できるが、参考にするためだけにmergeやcherry-pickを行わない。

## 意味を保って配置する

新しい定義が必要なら、対象ユースケースを実現する所有機能の実際のコードへ置き、利用者に必要なものを公開窓口からexportする。配置名はプロジェクトの規約を使い、文書の `domain/`・`application/` 等を実装へ機械的に複写しない。

型の構造・フィールド・選択肢・メソッドを保つ。既存schemaから導出する場合も同じ契約になることを確認する。SDKやDBの型への依存が見つかったら、単なる移動で依存ルールを満たしたとせず、必要な契約変更と依頼範囲を照合する。

型だけの契約は型だけで配置してよい。移管のためにダミーの実行処理、架空の成功結果、DB・CLI・依存パッケージを追加しない。数値範囲・日付・現在の許可等の実行時制約は、既存の検査や文書に維持する。静的な型だけで実行時の保証が増えたと説明しない。

文書の全文定義は、コードへの相対リンクと役割・所有者の説明へ置き換える。文書にはユースケースの目的、業務上の意味、判断理由、完了条件、例外・再開、型で表せない実行時制約を残す。別の型一覧を正本として複製しない。比較用の例を残すなら、現行契約ではないことを明記する。

## 検証して引き渡す

公開窓口・配置・許可依存を変えたら、構成規約・既存の境界設定・構造テスト・資料索引と参照を同じ差分で整合させる。共有ファイルの変更は必要な箇所に絞る。

通常のcheck・型検査と、変更に必要な既存テストを実行する。境界変更の禁止例による検証は [検証と完了](../SKILL.md#検証と完了) に従う。契約を移しただけなら未実装ユースケースの成功を模したテストは追加しない。相対リンク・見出し参照を確認し、図を変えた場合は描画と本文との整合も確認する。

移管済み・未移管の対象、保留した仕様、実行時検査の所在と限界、実施した検証を示す。型契約の配置と、ユースケース・アダプターの実装や実サービス受入の完了を分ける。契約の移管自体は、外部サービスへの実接続・資料送信・保存等の操作許可を追加しない。
