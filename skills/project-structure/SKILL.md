# Project Structure

機能の発見容易性・変更局所性・検証可能性を揃える。責務と依存方向を共通ルールとし、配置は言語・フレームワークに適応させる。

## 入力・出力・必要な能力

- 入力: 対象プロジェクト、用途、言語・フレームワークとバージョン、既存構成・規約、依頼範囲。既存ファイルから分かる情報を調査し、結果が変わる不足だけ確認する。
- 出力: 構成案と理由、モジュール境界・公開窓口・依存方向、検証方法。適用を依頼された場合は変更、採用規約と作業指示の記録、実施した検証と未完了事項まで含む。
- 必要な能力: 提供資料・ファイルの読取。技術固有の判断には現行の公式資料の参照。適用には編集・コマンド実行、CI接続には対象の設定編集が必要。利用環境の能力とスキル探索で解決する。資料取得不能なら未確認の仕様を示し、検証・編集不能なら該当操作を未完了として提案を渡す。未実施を成功扱いしない。

## 共通ルール

- **責務でまとめる。** 業務上の責務をモジュール、個々の業務操作をその内部の機能とする。CLI・ライブラリでは利用者に提供する能力で分ける。機能の実装とテストへの入口をたどれるようにする。
- **小さく始める。** 単一アプリを既定とし、モジュールを持つ場合も同じアプリ内で扱える。`apps/`・`packages/`、独立サービス、固定の `domain/usecase/adapter`、Repository・Serviceは実際の責務や分離の必要性があるときだけ導入する。既存の配備構成変更は依頼範囲から判断する。
- **境界を守る。** 他モジュールは公開窓口経由で利用する。公開窓口は普通の関数や型でもよい。内部実装や所有データを直接操作せず、モジュール間の依存を循環させない。複数モジュールの処理を調整する責務とトランザクション範囲を明示する。
- **判断を検証しやすくする。** 複雑な業務判断はHTTP・DB・外部APIから分離する。単純なCRUDにはフレームワーク標準を使える。抽象化や層は責務・検証・変更の必要性から選ぶ。
- **共有には所有理由を持たせる。** 複数モジュールで共有する理由のある基盤・汎用部品だけを共有領域へ置く。所有者の明確な業務処理はそのモジュールへ置き、共有領域から業務モジュールへの逆依存を作らない。
- **技術の制約に合わせる。** 予約ファイル・自動検出・パッケージング・実行環境の境界を保つ。採用技術の具体的な配置を決めるときだけ [構成例](references/layouts.md) の該当節を読む。例は必須テンプレートではなく、未掲載の技術にも同じ原則を対応させる。

## 依頼範囲を区別する

| 依頼 | 行うこと |
| --- | --- |
| 相談・構成提案 | 構成、境界、検証案を提示する。ファイル変更や採用記録は行わない |
| 新規構成の採用・適用 | 依頼されたコード・設定・検証を用意し、採用規約と継続利用の指示を記録する |
| 既存への明示的な適用 | 指定範囲を実際に組み替えるリファクタリングとして進める。全体への適用なら全体を対象とする |
| 採用後の通常変更 | 採用済み規約を維持して変更する。スキルの再利用や更新だけで構成を選び直さない |

既存への適用は提案だけで終えず、外部から見える振る舞い・公開契約・既存データを維持して進める。仕様変更やデータ変換は別の要求として扱う。通常変更中に構成の問題を見つけても、それだけで全体リファクタリングへ拡張しない。

## 構成の設計・適用

既存の作業指示と設計の正本を読み、エントリーポイント、機能の所有者、公開窓口、呼び出し元、テスト・ビルド・CIを調べる。外部公開されたimport pathやURL、migrationの識別子も変更影響に含める。

責務から必要最小限のツリーを組み、どのフォルダが技術上必須で、どれが設計上の選択か説明する。モジュールごとに所有する処理・データ、公開窓口、許可する依存先、テストの入口を定める。UIとAPIで同じ業務名を使っても、配置や粒度を機械的に一致させる必要はない。

適用では関連するimport・呼び出し元・設定・fixture・テスト・文書を整合させる。移動だけで検出不能になるテストや、自動検出・起動・配布の入口も確認する。migration済みデータを維持する移動と、DBの作り直しを混同しない。

## 採用を記録し、継続して守る

相談だけでは採用扱いにしない。新規構成の採用または既存への適用時には、次の両方を更新する。既存指示を保持し、関係する範囲に追記する。

1. **具体的な構成規約の正本。** 既存の設計文書と保存先の方針を優先する。正本がなければ `ARCHITECTURE.md` を候補とする。採用範囲、配置と責務、公開窓口・依存方向、データ所有者、検証入口、理由のある例外・移行中の範囲を記録する。コードや設定から安価に取得できる一覧は複製せず参照する。
2. **`AGENTS.md` 等の作業指示。** 構成設計・機能追加・配置変更・リファクタリングで本スキルを使うこと、コード変更で採用済み構成規約に従うこと、その正本への参照を短く明記する。既存の指示ファイルがあればそれを使い、別runtimeの指示ファイルやグローバル設定を追加しない。

正本が `ARCHITECTURE.md` である場合の記述例。文書パスとスキル参照は実際に解決できるものへ置き換える。

```markdown
## プロジェクト構成

- 構成設計・機能追加・配置変更・リファクタリングでは
  project-structure スキルを使用する。
- コード変更では [構成規約](ARCHITECTURE.md) の境界・配置・依存ルールに従う。
- 構成ルールを変更するときは、正本・実装・検証を整合させる。
```

ローカルマシン固有の絶対パスを採用指示に埋め込まない。スキル名と利用環境で解決できる参照を用い、参照先を確認する。スキルを利用できない場合もプロジェクトの構成規約は読めるようにし、その旨を報告して通常変更では規約を維持する。根拠が不足する構成変更は未完了とする。

スキルの更新は採用済み規約を自動的に上書きする理由にならない。既存規約との矛盾を示し、依頼された構成変更の範囲で正本・実装・検証を一緒に改訂する。提案・仕様・計画の保存先には対象プロジェクトの方針を使い、特定のIssue管理やWiki配置を強制しない。

## 検証と完了

適用には、重要な公開境界・依存方向・循環を機械的に検証する仕組みと、必要な振る舞いのテストを含め、既存の検証入口とCIへ接続する。既存ツールで表現できるなら再利用し、フォルダ整理だけを理由に新しい依存や独自パーサーを追加しない。

選んだ構造検証が禁止依存を検出することは、隔離したfixtureや一時的な違反を与えて失敗を確認し、その違反を残さずに正常な検証を通す。ファイル名や文書の存在確認だけを境界検証と呼ばない。import検証だけではDBの直接操作等を証明できないため、データ所有やトランザクションの規則には対応するテスト・確認も選ぶ。

完了時には対象範囲の実装・呼び出し元・設定・テスト・文書の整合、採用指示と正本の参照解決、実行した検証を確認する。構成ルール、振る舞い、起動・ビルド・配布のうち影響する項目を検証し、CI設定とCI上での成功を区別して報告する。必要な検証やCI接続ができなければ、その部分を未完了として示す。
