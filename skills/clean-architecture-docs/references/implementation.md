# 配置・境界・検証の判断

実装の構成提案・適用、フォルダ分割、設計との対応確認で読む。実在する責務だけを配置し、既存の採用方針と技術上の予約配置を優先する。

## 最上位の配置を決める

代表的なユースケースを一つ選び、入口、実行順と分岐、主な呼出し先、結果の行き先を確認する。入力から成果までを担う機能、提供元との接続や保存方式を担う実装、機能に依存しない共有部品について、それぞれの所有者と変更理由を確認する。

| 配置の候補 | 適する条件 |
| --- | --- |
| 機能別 | 機能ごとに入口と成果があり、その手順・規則・専用の接続を一緒に変更し、検証することが多い |
| 層別 | 入力形式や保存方式の変更を担当の層に閉じ込めやすく、個々のユースケースの入口から関係する層までを索引で辿れる |
| 機能別と層別の組合せ | 機能ごとの入口をまとめつつ、複数の機能が使う接続や基盤を、それぞれの所有責務で管理する必要がある |

たとえば、独立したワークフローが複数あるリポジトリでは、各入口と進行処理を `src/workflows/` にまとめ、判定モデルやエージェント製品への接続を `src/integrations/` に置く案がある。担当エージェントを選ぶ機能は、判定結果を受けて実行か保留かを決める。接続側は外部要求・応答の変換と送信を担う。

各グループの名前と階層は、対象の用途・規模・既存の規約に合わせる。一つの機能に固有の接続は、その機能内に置く案も検討する。単一の入口から処理を追える小規模な構成では、その入口と専用の処理を近くに置くだけでもよい。

配置案ごとに、最上位の各ディレクトリの役割を一文で説明し、実装索引から代表的な入口と呼出し先を実ファイルまで辿れるかを確かめる。依存方向はファイルの参照と注入で確認する。[ポートの共有と公開窓口](#ポートの共有と公開窓口)

### 層別の配置例

```text
src/
  domain/                    業務の値・不変条件・状態遷移
  application/
    contracts/               公開要求・結果・観測DTO
    ports/                   利用側が要求する外向き能力
    use-cases/               業務の手順・組合せ・結果集約
    execution/               必要な場合の中立な実行寿命管理
  adapters/
    inbound/                 CLI・HTTP等の形式検査と委譲
    outbound/                SDK・DB・OS等の具体I/O
  bootstrap/                 具象実装の生成・注入・起動
```

この配置では、最上位で層を選び、層内では業務の所有者や能力から探す。同じ業務の変更が複数層へ分かれるため、公開窓口と所有者を辿れる案内を用意する。`execution/` や `contracts/` は、独立して扱う責務がある場合に設ける。

## 実装レイヤーの README

レイヤー全体の位置づけから個々の実装ファイルへ辿れる順に、次の内容を記載する。

- **レイヤーと設計の対応。** レイヤーの責務・公開境界・許可する依存を示し、対応する全体設計、ユースケース、契約などの正本の該当箇所へリンクする。
- **ファイルと設計の対応。** 各実装ファイルへのリンクを置き、そのファイルが具体化する設計の節を示す。専用の設計節がない補助ファイルは、どの公開操作や規則を支えるかを示し、その根拠へつなぐ。根拠を確認できない箇所は未確認と記す。
- **ファイルの役割。** 各ファイルが担う処理・規則・契約と、入口や入出力のうち読者がコードを辿るのに必要な内容を短く記す。
- **ファイル間の関係。** 主要な入口、処理、規則、契約、具象、共有部品を実ファイル名またはパスで示す。直接の呼出し・型や設定の参照、ポートの実装・具象の注入、実行時の読み込み、データの受け渡しをコードで確認し、該当する関係を Mermaid で示す。直接の import と間接的な呼出しが区別できるよう、矢印の意味と向きを明記する。

ファイル依存はフローチャート、呼出しの時間順はシーケンス図で示せる。全体ではレイヤーをまたぐ関係を示し、各 README ではそのレイヤーで処理や型を追える深さまで掘り下げる。線が多い図は、実行・保存・参照など読む目的ごとに分ける。正本に同じ関係の図があればリンクし、補助的な依存は本文のソースリンクから辿れるようにする。

設計の詳細は正本へリンクし、README には実装を読むための対応と要点を残す。設計とソースへのリンクは [リポジトリ内のリンク](documentation.md#リポジトリ内のリンク) の規則に従う。ファイルの追加・移動・責務変更で対応が変わったら、同じ変更で対象 README を更新する。

## 実装を進める順序

森から木へ、全体の実行骨格 → 個別UC → UC内部の処理 → 接続実装の順に進める。

1. **全体の実行骨格。** 採用済みの入力・結果・責務を使い、依頼受付、実行管理、全体制御、UCの呼出し境界、結果集約と返却をつなぐ。呼出し先は注入できる境界とし、テスト用fakeで呼出し・集約・停止を検証する。製品の未実装処理は未対応として返す。骨格は実際に呼出しと返却を確認できるもので、空フォルダの一式ではない。
2. **個別UC。** 骨格と必要な詳細設計が揃い、入力・成果・責務・例外・再開の整合を確認してから、骨格に接続するUCの手順を実装する。着手条件は対象の採用済み方針に従う。
3. **UC内部の処理。** UC全体の流れから業務規則、検査、状態遷移、記録へ具体化し、所有する設計の受入ケースに対応付ける。
4. **接続実装。** 利用側ポートに沿って具体的なSDK・DB・OSの実装を接続し、変換・失敗・権限と統合時の振る舞いを検証する。

骨格実装と個別UC・接続の詳細設計は並行できる。個別の設計完了だけで詳細実装へ進まず、全体で利用する位置と着手条件を確認する。骨格に必要な契約自体が未決なら、その部分を所有する設計で解消する。既存への部分変更では、既存の骨格と対象UCの関係を先に確認し、必要な範囲をこの順序で掘り下げる。

## ファイルの配置を決める

| 判断する対象               | 配置の判断                                                  | 避ける判断                                     |
| -------------------------- | ----------------------------------------------------------- | ---------------------------------------------- |
| 不変条件・計算・状態遷移   | I/Oから独立した規則はdomain。業務固有ならその所有者の内側   | schema・業務名があるというだけでdomainへ集める |
| 依頼・応答・観測値         | applicationのcontracts。domainの値は参照・必要な変換で使う  | 同じ値・規則のschemaを層ごとに複製する         |
| 複数操作の組合せ・成果集約 | applicationのuse-cases。業務の採否はUC／domain              | controllerや外部接続へ判断を置く               |
| 外部へ要求する能力         | 利用側のports。メール読取・ファイル取得等の能力名で探せる形 | 提供元SDKをそのまま抽象化した万能API           |
| 停止・取消・資源終了・排他 | 業務結果に依存しない手順ならapplicationのexecution          | 終了処理へ特定UCのResult生成や完了判定を混ぜる |
| SQL・SDK・認証・HTTP変換   | adapters/outbound。外部表現は境界で変換する                 | SDK型・SQL行・token・生DBを内側へ公開する      |
| 起動・具象選択             | bootstrap。普通のfactoryと引数注入で足りる場合はそれを使う  | 内側がbootstrapへ戻って依存を取得する          |

例えば観測した金額と欠落のDTOはcontracts、計算上の不変条件を持つ金額モデルはdomainである。同じ用語でも用途と変更理由で分ける。domainからcontractsへの依存が必要になったら、内側へ置くべき値・規則がないか調べ、定義を複製せず依存を反転する。

## 業務判定と実行遷移

- **domain** は、処理を進められるか、省略できるかなどを、確認済みの業務事実から純粋な規則で判定する。入力を判定に必要な事実に絞り、業務上の意味を持つ値を返す。
- **application** は、所有側の公開操作やポートを通じて記録を取得し、依頼の対象・版・確定参照との一致や、必要な引渡し・記録更新の成立を確認する。判定に使う事実をdomainに渡し、整合確認と業務判定の結果をワークフローへ返す。
- **ワークフロー** は、結果に応じて後続処理、既存成果の照会、再実行、保留、終了を選ぶ。実行中の状態には分岐に必要な値を置き、再開時は業務記録の正本から状態を構成する。グラフを採用する場合は、再開点と副作用の境界に沿ってノードを分け、実行順を遷移の定義から辿れるようにする。

domainの判定表、applicationの整合確認、公開入口からの遷移を対応付けて検証する。該当する場合は、処理不要が確定したとき、引渡しが競合したとき、外部送信の結果照会だけを行うときを取り上げ、各経路で呼ぶ操作と返す結果を確認する。

## 契約を意味と変更理由で分ける

契約が増えたら、契約の意味を所有する責務と、何の変更で契約が変わるかを確認する。次の区分は配置の判断例。独立したフォルダにするかは、対象の責務と依存制約に合わせて決める。

| 区分の例 | 変更理由 | 契約の例 |
| --- | --- | --- |
| `business` | 個別業務の要求・成果・観測が変わる | 業務操作の要求・結果、取得候補 |
| `orchestration` | アプリ全体の受付・組合せ・再開が変わる | 全体の要求・結果、未着手工程、子の成果の集約 |
| `capabilities` | 支援能力の入出力が変わる | 一時ファイル、取得した時刻、対象・操作・版に対する現在の許可 |
| `runtime` | 業務に依存しない実行上の約束が変わる | 共通エラー、停止設定 |

- 複数のUCで使う結果でも、業務成果を表す契約は業務側が所有する。個別UCは自分の成果と保留条件を返し、全体制御が各成果を集約して未着手工程と再開先を決める。依存は全体制御から個別業務へ向ける。
- 関連する公開操作とデータは、所有業務の中で役割ごとにまとめる。UC番号・ファイル数・呼出し元の数だけでサブフォルダや共通領域へ移さない。共有する対象・版の定義が必要なら、それを所有する定義元を一つにする。
- 支援能力の受け渡しデータは意味の所有者に置き、そのデータを使うメソッドは利用側ポートに置く。実行設定と寿命管理の手順も区別する。業務非依存の実行契約を設ける場合は業務契約から独立させ、区分間で許可する参照を明示する。

## ポートの共有と公開窓口

利用側所有は、一つの業務だけから利用可能という意味ではない。要求範囲、版、返却値、失敗、許可条件が一致する複数UCは同じ能力ポートを利用できる。能力別ファイルを `application/ports/` 直下に置く構成を候補とし、利用元の業務名による囲込みを自動的に作らない。

同じ「メール」でもラベル書込付きと読取専用では要求が異なる。同じAIを使っても候補判定と別業務の判断では契約が異なる。必要ならポートを分け、同じ接続実装が両方を提供できる。ポートの共有と接続実装の共有は別々に判断する。純粋なdomain規則は通常の関数・値として使い、差し替える必要のない規則まで外向きポートにしない。

公開窓口は所有する関数・型のファイルでよい。全内部を再exportするindexや転送だけのapiファイルを必須にしない。別の業務所有者の内部表・SQL・実行graphを直接呼ばず、その公開操作を使う。層が同じことは、他業務の内部へのアクセス許可にならない。

## ユースケースの実装境界を決める

一つの手順と直接テストで完結するなら `use-cases/` 直下に置ける。手順と専用の補助処理を一緒に変更・検証する場合や、業務の内側に閉じる依存を明示したい場合は、所有業務のフォルダにまとめる。全体制御や他のUCが使う公開操作と、bootstrapが依存を注入する箇所を示す。

他の業務には公開操作または参照ポートを通して接続する。所有業務内の専用補助や全体制御内の選択・集約の補助を直接参照する場合は、呼出し元と参照先を明示する。境界検査では、UCから別業務の手順を直接参照する例と、bootstrapからUC内部の補助を直接参照する例が拒否されることを確かめる。

## 依存・データ・寿命

- domainはapplication・adapters・bootstrap・具体I/Oへ依存しない。applicationはdomain・純粋な契約・必要ポートを使い、adapters・bootstrapへ依存しない。adaptersは内側の契約を使い、bootstrapが具象を注入する。
- 値importだけでなく、型import、再export、動的import、aliasも境界に含める。型だけの循環も避ける。製品コードから検証コードへ依存しない。
- データごとに業務上の意味の所有者と、SQL・永続操作の所有者を明示する。同じDBにあることを他機能の表を更新する許可にしない。生DBや任意SQL／transactionコールバックを渡すことで所有境界を迂回しない。
- 一緒に確定すべき状態は、意味のある一つの操作と短いtransactionで扱う。ネットワーク・AI・人待ちをtransactionに含めない。ファイルやRepositoryの数に合わせて原子性を分断しない。
- 資源取得、context終了、記録、DB close、結果出力、排他解放の必要な順序を採用設計から確認する。具体的な順序は製品契約に従い、出力・記録のやり直しを理由に業務の副作用を再実行しない。

## 適用と検証

変更前の設計を基準に公開契約、呼出し元、固定データ、既存データ、起動・配布・テスト検出への影響を確認する。フォルダ移動でDBを作り直さず、データ移行が必要なら明示する。公開path・CLI等の互換を残すかは対象の要件で決める。

直接テストは所有実装の近く、共有fixtureは検証用の共通領域、横断する構造検査は全体の検証入口から辿れる位置を候補とする。フォルダの形やファイルの存在だけを境界検証と呼ばない。

境界は既存のlint・依存検査で実際のソースを検査し、主要な禁止依存と循環が検出されることを最小限の隔離fixture等の反例で確かめる。正常例と違反除去後の成功も確認する。import検査で証明できないデータ所有・rollback・寿命は対応する振る舞いの検証で補う。新しい依存や独自パーサーは必要性がある場合だけ追加する。

コード変更に伴う検査は影響範囲に合わせ、fakeポートで成果・部分成功・例外・再開、adapterの契約テストで変換・失敗を検証する。必要な起動・ビルド・配布、既存のCI入口も整合させる。資料のみの変更に無関係な実行テスト一式を課さない。検査の成功と、設計で求める成果・例外・責務との適合確認を別々に報告する。
