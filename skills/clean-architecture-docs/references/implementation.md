# 配置・境界・検証の判断

実装の構成提案・適用、フォルダ分割、設計との対応確認で読む。層別の候補は次のとおり。実在する責務だけを配置し、既存の採用方針と技術上の予約配置を優先する。

```text
src/
  domain/                    業務の値・不変条件・状態遷移
  application/
    contracts/               公開要求・結果・観測DTO
    ports/                   利用側が要求する外向き能力
    use-cases/               業務の手順・組合せ・結果集約
    execution/               必要な場合の中立な実行寿命管理
  adapters/
    inbound/                 CLI・HTTP等の形式検査と委譲
    outbound/                SDK・DB・OS等の具体I/O
  bootstrap/                 具象実装の生成・注入・起動
```

最上位は役割から探し、層内では業務所有者や能力で探せるようにする。同じ業務の変更が複数層へ分かれるため、公開窓口と所有者を辿れる案内を用意する。層別が開発速度や性能を必ず改善するとは主張しない。`execution/` や `contracts/` の独立が不要な規模では、名前を揃えるためだけに分割しない。

## 実装を進める順序

森から木へ、全体の実行骨格 → 個別UC → UC内部の処理 → 接続実装の順に進める。

1. **全体の実行骨格。** 採用済みの入力・結果・責務を使い、依頼受付、実行管理、全体制御、UCの呼出し境界、結果集約と返却をつなぐ。呼出し先は注入できる境界とし、テスト用fakeで呼出し・集約・停止を検証する。製品の未実装処理は未対応として返す。骨格は実際に呼出しと返却を確認できるもので、空フォルダの一式ではない。
2. **個別UC。** 骨格と必要な詳細設計が揃い、入力・成果・責務・例外・再開の整合を確認してから、骨格に接続するUCの手順を実装する。着手条件は対象の採用済み方針に従う。
3. **UC内部の処理。** UC全体の流れから業務規則、検査、状態遷移、記録へ具体化し、所有する設計の受入ケースに対応付ける。
4. **接続実装。** 利用側ポートに沿って具体的なSDK・DB・OSの実装を接続し、変換・失敗・権限と統合時の振る舞いを検証する。

骨格実装と個別UC・接続の詳細設計は並行できる。個別の設計完了だけで詳細実装へ進まず、全体で利用する位置と着手条件を確認する。骨格に必要な契約自体が未決なら、その部分を所有する設計で解消する。既存への部分変更では、既存の骨格と対象UCの関係を先に確認し、必要な範囲をこの順序で掘り下げる。

## ファイルの配置を決める

| 判断する対象               | 配置の判断                                                  | 避ける判断                                     |
| -------------------------- | ----------------------------------------------------------- | ---------------------------------------------- |
| 不変条件・計算・状態遷移   | I/Oから独立した規則はdomain。業務固有ならその所有者の内側   | schema・業務名があるというだけでdomainへ集める |
| 依頼・応答・観測値         | applicationのcontracts。domainの値は参照・必要な変換で使う  | 同じ値・規則のschemaを層ごとに複製する         |
| 複数操作の組合せ・成果集約 | applicationのuse-cases。業務の採否はUC／domain              | controllerや外部接続へ判断を置く               |
| 外部へ要求する能力         | 利用側のports。メール読取・ファイル取得等の能力名で探せる形 | 提供元SDKをそのまま抽象化した万能API           |
| 停止・取消・資源終了・排他 | 業務結果に依存しない手順ならapplicationのexecution          | 終了処理へ特定UCのResult生成や完了判定を混ぜる |
| SQL・SDK・認証・HTTP変換   | adapters/outbound。外部表現は境界で変換する                 | SDK型・SQL行・token・生DBを内側へ公開する      |
| 起動・具象選択             | bootstrap。普通のfactoryと引数注入で足りる場合はそれを使う  | 内側がbootstrapへ戻って依存を取得する          |

例えば観測した金額と欠落のDTOはcontracts、計算上の不変条件を持つ金額モデルはdomainである。同じ用語でも用途と変更理由で分ける。domainからcontractsへの依存が必要になったら、内側へ置くべき値・規則がないか調べ、定義を複製せず依存を反転する。

## ポートの共有と公開窓口

利用側所有は、一つの業務だけから利用可能という意味ではない。要求範囲、版、返却値、失敗、許可条件が一致する複数UCは同じ能力ポートを利用できる。能力別ファイルを `application/ports/` 直下に置く構成を候補とし、利用元の業務名による囲込みを自動的に作らない。

同じ「メール」でもラベル書込付きと読取専用では要求が異なる。同じAIを使っても候補判定と別業務の判断では契約が異なる。必要ならポートを分け、同じ接続実装が両方を提供できる。ポートの共有と接続実装の共有は別々に判断する。純粋なdomain規則は通常の関数・値として使い、差し替える必要のない規則まで外向きポートにしない。

公開窓口は所有する関数・型のファイルでよい。全内部を再exportするindexや転送だけのapiファイルを必須にしない。別の業務所有者の内部表・SQL・実行graphを直接呼ばず、その公開操作を使う。層が同じことは、他業務の内部へのアクセス許可にならない。

## 依存・データ・寿命

- domainはapplication・adapters・bootstrap・具体I/Oへ依存しない。applicationはdomain・純粋な契約・必要ポートを使い、adapters・bootstrapへ依存しない。adaptersは内側の契約を使い、bootstrapが具象を注入する。
- 値importだけでなく、型import、再export、動的import、aliasも境界に含める。型だけの循環も避ける。製品コードから検証コードへ依存しない。
- データごとに業務上の意味の所有者と、SQL・永続操作の所有者を明示する。同じDBにあることを他機能の表を更新する許可にしない。生DBや任意SQL／transactionコールバックを渡すことで所有境界を迂回しない。
- 一緒に確定すべき状態は、意味のある一つの操作と短いtransactionで扱う。ネットワーク・AI・人待ちをtransactionに含めない。ファイルやRepositoryの数に合わせて原子性を分断しない。
- 資源取得、context終了、記録、DB close、結果出力、排他解放の必要な順序を採用設計から確認する。具体的な順序は製品契約に従い、出力・記録のやり直しを理由に業務の副作用を再実行しない。

## 適用と検証

変更前の設計を基準に公開契約、呼出し元、固定データ、既存データ、起動・配布・テスト検出への影響を確認する。フォルダ移動でDBを作り直さず、データ移行が必要なら明示する。公開path・CLI等の互換を残すかは対象の要件で決める。

直接テストは所有実装の近く、共有fixtureは検証用の共通領域、横断する構造検査は全体の検証入口から辿れる位置を候補とする。フォルダの形やファイルの存在だけを境界検証と呼ばない。

境界は既存のlint・依存検査を使い、主要な禁止依存と循環が失敗になることを隔離fixture等の反例で確かめる。正常例と違反除去後の成功も確認する。import検査で証明できないデータ所有・rollback・寿命は対応する振る舞いの検証で補う。新しい依存や独自パーサーは必要性がある場合だけ追加する。

コード変更に伴う検査は影響範囲に合わせ、fakeポートで成果・部分成功・例外・再開、adapterの契約テストで変換・失敗を検証する。必要な起動・ビルド・配布、既存のCI入口も整合させる。資料のみの変更に無関係な実行テスト一式を課さない。検査の成功と、設計で求める成果・例外・責務との適合確認を別々に報告する。
