# 資料の責務と読み順

設計資料を新設・分割・統合・移動する場合に読む。以下は構成候補であり、既存の正本と資料配置を優先する。

## 設計を進める順序

森から木へ、全体 → UC間の関係・責務 → 個別UC → 内部規則・契約 → 接続・実行・永続化の詳細の順に具体化する。まず目的・対象／対象外・全体の入口と成果を示し、各UCがどの成果を担うか、どう組み合わさるかを整理する。その境界に沿って個別の入力・完了条件・例外・再開を定め、必要な詳細設計へ進む。

詳細資料を先に増やして全体像を後付けしない。各詳細では、具体化する上位の成果・責務と、その設計の前提を明示する。掘り下げて全体との矛盾が分かったら所有する上位設計へ戻して判断し、関連するUC・契約・図を揃える。読み順と設計順の両方が全体から個別へ辿れるようにする。

## 読み順と所有する内容

| 資料                      | 所有する内容                                                 | 別資料へ委ねる内容                     |
| ------------------------- | ------------------------------------------------------------ | -------------------------------------- |
| 全体設計・索引            | 目的、対象／対象外、全体図、現在地、正本への入口             | 個々のUCの判断条件の全文               |
| UCの全体入口              | UC一覧、共通前提、UC間の組合せ、詳細への導線                 | 個別UCの本文の複製                     |
| 個別UC                    | 利用者、起点、入力、業務手順、成果、完了・保留・例外、再開先 | SDKのメソッド・SQL・実装nodeの割付け   |
| UC固有の規則・論理契約    | 不変条件、状態遷移、採否、照合条件、受入ケース               | 同じ業務を説明する別工程体系           |
| applicationの契約・ポート | 公開要求・結果、外部へ要求する能力、失敗・未対応・権限条件   | 提供元SDKの型や認証token               |
| adaptersの設計            | API・認証・変換、提供元の制約、通信や部分取得の報告          | 業務上の対象選定・完了判定・再送の採否 |
| architecture              | モジュール責務、公開境界、依存方向、配置、データ所有         | UCの業務フローの再定義                 |
| infrastructureの設計      | 実行・記録・一時物等の具体方式                               | 業務の成果を独自に完了とする判断       |
| research・過去レビュー    | 確認した一次資料・時点・限界、当時の判断根拠                 | 現行仕様の並行管理                     |

文書の `infrastructure/` があるからといって、コードにも同名の最上位を作る必要はない。文書は読者の論点、コードは処理と変更の所有に合わせる。UC・モジュール・実行node・transactionを1対1にしない。

新規なら、例えば `DESIGN.md` を全体入口とし、対象レイヤーに対応する `docs/design/domain.md`、`docs/design/application.md`、`docs/design/adapters.md` などへリンクする。個別UCや接続設計などの詳細資料は、必要に応じて `application/use-cases/` や `adapters/` などに置き、対応するレイヤー文書から参照する。レビュー成果物は現行設計と区別した場所に置く。特定のレビュー製品名を保存先の必須条件にしない。

## UCを具体化する観点

- 誰が、どの起点で、何を入力するか。対象・範囲・版の指定が必要か。
- 何が成果として残り、何を観測すれば完了か。外部受付・保存・照合・業務完了を区別する。
- 部分成功、未対応、保留、失敗、取消をどう返すか。既存成果と残件を失わないか。
- 例外後に何を再確認し、どこから再開するか。外部へ送信済みか不明な場合、照合と新規送信を区別できるか。
- 詳細資料が具体化するUC・成果・完了条件はどれか。同じ規則を別の資料へ複製していないか。

型やschemaは形式の検査であり、対象の実在・現在権限・版の一致・業務完了までは保証しない。文書には型で表せない意味・実行時条件・採用理由を残す。既存の型／interface／schemaは所有するソースへリンクし、文書・fakeの別定義を正本にしない。

## 図とリンク

全体・UCの冒頭図には入口、主要処理、責務境界、条件分岐、成果／保留、必要な再開先を示す。Markdown では `mermaid` コードブロックを使う。関係や分岐にはフローチャート、呼出し順や寿命にはシーケンス図、状態遷移には状態図など、論点に合う図を選ぶ。矢印が業務やデータの流れ、実行時の呼出し、ソース依存、生成／注入のどれを示すか明記する。実装の図は現行コードに照合し、未実装の設計を載せる場合はそのことを図の近くに明記する。

固有規則の詳細は所有UCの図へリンクする。全体から詳細、詳細から全体、他UCを利用する箇所からそのUCへ辿れるようにする。図のクリック先だけに導線を閉じず、本文にもリンクを用意する。

## リポジトリ内のリンク

同一リポジトリ内の設計文書・README・ソースへのリンクは、リポジトリルートからの実在するパスで参照先を特定し、表示環境が解決できる相対リンクで記載する。ディレクトリとファイル名を含め、別の環境でチェックアウトした読者も辿れるようにする。

- **GitHub 上のリポジトリ内 Markdown。** `[全体設計](/docs/design/overview.md)` のようにリンク先を `/` から始めるとリポジトリルート基準になる。ローカルなどでも読む文書では、リンク元ファイルからの `./` や `../` を使う。たとえば `src/application/README.md` からは `[全体設計](../../docs/design/overview.md)` と書く。節を指すときは表示環境の見出しアンカーを確認する。
- **Obsidian 保管庫内の文書。** 保管庫の規約と利用可能な `obsidian-markdown` に従う。ウィキリンクは保管庫ルートからのパスと実際の見出し名を使う。リポジトリ全体が保管庫なら `[[docs/design/overview#処理の流れ]]`、`docs/` が保管庫なら `[[design/overview#処理の流れ]]` と書く。表内で表示名を付ける場合は区切りの `|` をエスケープする。

スキル自身の `SKILL.md`・参照ファイル・UI設定は、ディレクトリごと持ち出せるよう通常のファイル相対 Markdown リンクと所定の frontmatter を使う。

## 整理時の確認

移動・改名前に固有規則・未決事項・検証根拠と参照元を調べる。内容の移管と索引・本文・図のリンク更新を同時に行う。履歴は当時の記録として保持し、現行の別仕様として更新しない。旧ファイルやアンカーを残すかは展開先の互換要件で決める。

「M1の起動と観測」のような名称は「実行の起動と稼働観測」のように、読者が機能から探せる形へ直す。本文も過去の実装時期から書き起こさず、現行の入出力・関係と利用条件を記す。初回保存やプロトコルの版など、動作の理解に必要な順序・識別子は残す。

資料の検証では、追加・変更したリンクをそれぞれの基準位置から解決し、意図するファイル・見出しを指すことを確認する。表の列、図と本文、正本の重複も確認する。表示環境が使える場合は図の描画とリンクによる往復も確認する。静的検査と実際のレンダリング確認の結果を分けて報告する。

採用状態、設計完了、型・骨格の実装、個別UCの実装、実サービス受入は別々に示す。未決は「入出力・成果・責務を確定できないもの」と「確定した契約に沿う実装／運用前の確認」を区別する。後者には担当・停止条件・再開条件を残し、未回答を採用済みにしない。
