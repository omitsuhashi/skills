# ドキュメントと実装の構成設計

利用者の目的から、業務規則、公開契約、処理の所有者、具体的な接続まで辿れる構成にする。資料の分類とコードの配置は別々に設計し、責務と根拠で対応付ける。

## 入力・出力・必要な能力

- 入力: 依頼の目的・対象範囲、既存の全体設計・UC・構成規約、必要な実装・テスト・境界設定。指定版と採用状態を確認する。
- 出力: 相談なら構成案と理由・未決事項、資料整理なら正本・読み順・参照の更新、構成適用なら設計と配置の対応・対象変更・検証結果。設計資料の作成・整理や構成適用では、対象レイヤーの文書と、実装がある各レイヤーの `README.md` を成果物に含める。
- 必要な能力: 資料・コードの読取と構成設計。保存・適用には編集、コード変更の検証には対象の検査を実行する能力が必要。着手時に利用可能か確認し、正本を取得できなければ根拠を要する判断を未確定とする。編集・実行ができなければ提案・変更案まで示し、未適用・未検証の範囲を報告する。図の描画は利用可能な場合に確認し、使えなければソースを提示する。

## 設計も実装も、森から木へ進める

**設計・実装のどちらも、全体から個別へ段階的に具体化する。** 設計では、システム全体の目的・対象範囲・流れ・成果を先に捉え、UC間の関係と責務・公開境界を定めてから、個別UC、内部の規則・契約、接続・永続化の詳細へ進む。資料の読み順だけでなく、設計を決める順序にもこの方針を適用する。

実装では、採用済みの全体設計に沿って、依頼受付・全体制御・UCの呼出し境界・結果集約をつなぐ骨格を先に用意し、個別UC → UC内部の処理 → 具体的な接続へ進む。個別機能の設計が完了したことだけを理由に、その詳細実装を先行させない。骨格と詳細設計は並行して進められるが、詳細実装へ入る前に、骨格との入出力・責務・例外・再開の整合を確認する。

既存への部分変更でも、まず対象が全体のどこを担うかを確認してから掘り下げる。詳細で得た知見は全体へ戻して整合を取り、依頼範囲に必要な深さまで具体化する。全体から進めることを、無関係な範囲の全面再設計や空の雛形を作る理由にしない。

## 着手時に確認すること

- 対象の作業指示、全体設計、UC、採用済み構成規約、実装・テスト・境界設定を読む。提案・採用済み・実装済み・実サービス受入済みを区別する。
- 相談、資料だけの整理、コードを含む構成適用、採用後の通常変更のどれかを判断する。相談では提案まで、資料整理では文書と参照の更新まで、適用では指定範囲の変更と検証まで行う。
- 対象プロジェクトの作業規約から、全体設計・UC・構成規約・検証入口の正本を探す。本スキルの例で既存の採用方針を上書きしない。

## 設計の軸

1. **UCの成果から始める。** 利用者・起点・入力・成果・完了条件・例外・再開先を先に定め、その実現に必要な規則・能力・所有者を整理する。接続先の数やgraph nodeの数からUCやモジュールを決めない。
2. **規則ごとに正本を一つ持つ。** 業務フローと採否はUCとその固有規則、境界データと能力は公開契約、提供元のAPI・認証・変換は接続資料に置く。型定義が存在する場合はコードを参照し、文書やfakeへ再定義しない。
3. **依存は内側へ向ける。** domainは業務の値・不変条件、applicationは手順・契約・利用側ポート、adaptersは具体I/O、bootstrapは生成・注入を担う。実行時の呼出し方向とソースの依存方向を区別する。
4. **分割は変更理由で説明する。** 同じ業務名・純粋な型・同じSDKという理由だけでまとめない。公開窓口、許可依存、処理・データの所有、検証入口を示し、分ける／まとめる理由を述べる。
5. **配置だけで業務の保証を変えない。** 不可分な記録をフォルダ都合で別transactionにせず、生DBを公開して所有境界を迂回しない。未実装の能力を成功する仮処理で埋めない。
6. **業務判定・記録の整合確認・実行遷移を分ける。** domainは確認済みの事実から業務上の可否を判定し、applicationは記録の対象・版・確定状態を確認する。ワークフローは結果を受けて次の操作を選ぶ。分岐や再開を設計するときは [業務判定と実行遷移](references/implementation.md#業務判定と実行遷移) を読む。

## 作業に応じた進め方

設計資料の作成・整理や構成適用では、対象プロジェクトが採用するレイヤーごとに Markdown 文書を用意し、責務・公開境界・許可する依存と詳細の正本へのリンクを記載する。既存のレイヤー文書を更新し、不足分の命名と保存先は対象プロジェクトの規約に従う。

実装がある対象レイヤーでは、各レイヤーのディレクトリに `README.md` を作成・更新する。既存の設計文書があれば README から参照し、プロジェクトの規約に合えば README をレイヤー文書として使える。部分変更では対象レイヤーに絞り、実装前のレイヤーは設計文書で扱う。全体設計または索引からレイヤー文書と README へ辿れるようにする。[実装レイヤーの README](references/implementation.md#実装レイヤーの-readme) に沿って、設計と実装ファイルの対応を記載する。

### 設計資料を作る・整理する

[資料の責務と読み順](references/documentation.md) を読む。全体設計 → UC → 必要な規則・契約・接続・実行詳細への導線を作り、各判断の正本を明示する。文書の分割だけで実装境界を変えない。

README・ガイド・設計・契約の見出し、本文、図、ファイル名は、読者の目的や機能・責務で名付ける。マイルストーン名（M1など）、実装順、作業記録はIssue・PRや既存の履歴へ置く。現行文書には、使える機能と前提、未対応の挙動、未検証の受入条件など、読む人の判断に必要な状態を残す。

全体設計とUCの入口では、入口・主要処理・責務境界・結果の行き先を Mermaid で示す。実装索引と対象レイヤーの README では、主要ファイルを実名で示し、層内と層をまたぐ呼出し・ソース依存・ポート実装と注入を、確認できる範囲で Mermaid にする。実行順の図があっても、そこで読み取れないファイル間の関係は依存図などで補う。同じ観点の図が正本にあれば、該当箇所へリンクする。 [実装レイヤーの README](references/implementation.md#実装レイヤーの-readme)

### 実装の構成を設計・適用する

[配置・境界・検証の判断](references/implementation.md) を読む。契約を分けるときは意味の所有者と変更理由を、UCの実装を分けるときは公開操作と起動時の組み立て窓口を確認する。

新規の構成候補は層別を出発点とし、層内を実在する業務責務・能力で分ける。既存構成の変更は依頼範囲に合わせ、言語・フレームワークの予約配置を保つ。空の層、DTOの複製、転送だけの窓口、DIコンテナーを一式追加しない。

変更前の採用済み設計に対して、次の対応をPRまたは作業結果へ残す。既存の様式がある場合はそれを使う。

| 設計の根拠（パス・節・指定版） | 成果・責務                 | 配置と公開窓口         | 分割・統合の理由          | 依存・データ所有への影響         | 検証                         |
| ------------------------------ | -------------------------- | ---------------------- | ------------------------- | -------------------------------- | ---------------------------- |
| 対象UC／構成規約の該当箇所     | 今回担う処理と担わない判断 | 実ファイルと呼出し境界 | 変更のまとまり・I/O分離等 | 所有者・原子性・寿命の維持／変更 | 代表入力・期待結果・境界検査 |

採用済み責務の内側の分割は実装詳細として進める。責務・公開契約・依存方向・データ所有者を変える場合は設計変更として根拠を明示し、対象の設計判断の手順に従う。文書やlintを実装へ追従させただけで適合扱いにしない。

## 採用・検証・報告

- 構成を適用したら、対象の構成規約・実装・呼出し元・境界設定・必要な構造検査を同じ変更で揃える。継続指示は既存の `AGENTS.md` 等から正本へ短くリンクする。スキルの追加・更新だけをプロダクト構成の再採用と扱わない。
- 全体設計または索引から対象レイヤーの文書・README・ファイル間の図へ辿れることを確認する。主要な公開窓口・契約・具象を図で追え、矢印の種類と向きが現行コードに合うことを確認する。変更した現行文書の見出し・本文・図・パスに作業履歴や段階名が入り込んでいないか確認する。正本の重複、リンク・見出し、図と本文、未決事項の保持も確認する。コードでは重要な禁止依存の反例と、影響する成果・例外・原子性・寿命を検証する。コマンドは対象リポジトリの既存入口を使う。
- 完了時は変更内容と理由、設計への適合、実行した検査、残る未実装・未検証を分けて報告する。型・lint・fakeの成功を、業務完了や実サービス受入の証拠にしない。

## 他のリポジトリへ展開する場合

このスキルのディレクトリを一式で持ち出せるよう、手順は相対リンクで完結させる。参照元リポジトリの業務名・DB名・Issue番号・ツール・互換経路の撤去方針は共通要件にしない。展開先で採用するときに、その正本・技術・文書形式・互換要件へ対応付ける。コピーや外部公開は、その依頼がある範囲で行う。
