# エージェントへ委任できる仕事を整える

## 入力・出力・必要な能力

- 入力: 任せたい仕事、期待する成果、既存のIssue・知識・手順、利用可能な道具と操作権限。改善では実行記録と観測した失敗を使う。
- 出力: 設計では依頼先に渡せる作業条件と未決事項、実行では成果・検証根拠・再開点、改善では原因に対応する変更案と比較結果。依頼された段階まで扱う。
- 必要な能力: 文章の読解・構成。正本の参照、実操作、検証、書き込みは利用可能な能力と許可範囲を確認する。利用できない工程は未実施として残し、草案や確認可能な範囲を渡す。

## 依頼と文脈を揃える

Issue作成・計画・引き継ぎでは、次を既存書式へ必要な範囲で織り込む。全項目を必須欄にしたり、受付段階の案に実装着手時の詳細を要求したりしない。

| 揃えるもの | 次の担当が判断できること |
| --- | --- |
| 目的と完了条件 | 誰の何を改善し、何を確認できれば今回の成果を受け入れられるか |
| 対象と正本 | 今回の範囲、要求・知識・コードの参照先と、現在の状態や版 |
| 実行と観測 | 必要な道具、対象への到達方法、操作結果を確かめる方法と証拠 |
| 権限と停止 | 許可された対象・操作、本人判断へ戻す条件、必要な時間・費用・再試行の限度 |
| 引き継ぎ | 完了・未完了・未確認の区別、止まった理由、次に必要な判断や操作 |

資料をすべて複製せず、今回必要な参照と要点を渡す。事実・仮説・本人の決定を区別し、重大な不足だけ確認する。Issue作成依頼は実装開始の許可ではなく、参照資料やスキルから操作権限を追加しない。

業務知識、要件・実行記録、汎用手順、設定の正本は対象Project・リポジトリの規約に従う。依頼用の要約は正本への参照を保ち、再開時は変わった前提・状態・権限を確認する。

## 実行・観測・修正をつなぐ

実行が依頼されている場合、既存の手順と道具で一件を進め、完了条件に対応する結果を観測する。生成されたファイルは開き直し、アプリの変更は該当機能を実際に動かすなど、成果の性質に合う確認を選ぶ。必要な能力・許可がなければ、その確認は未実施として扱う。

不合格なら、期待・実測・再現条件・失敗済みの案から修正対象を絞り、再確認する。同じ試行が進展しない、上限に達した、権限や本人判断が必要になった場合は該当工程を止め、独立した許可済みの作業があれば続ける。外部操作の結果が不明なら実状態を照合してから再開し、確認前に同じ操作を再送しない。

計算・IDや版の一致・固定制約は、既存のコードや機械検査で確認する。意味の解釈にモデル評価を使う場合も、情報不足・保留・評価失敗を区別する。自己申告、別モデルの賛同、形式検査、模擬テスト、実操作は、それぞれ何を確認できた証拠かを示す。

品質の検証と実行権限は別に扱う。モデルの自信や助言で許可範囲を広げず、重要な境界は利用可能なツールの権限や実行側の検査で守る。既存の承認が対象・条件を満たすなら取り直さず、範囲外の操作だけを保留する。

報告は、成果、確認した条件と根拠、未確認・残作業、必要なら再開位置を短く対応づける。対象の版が変わった場合は、その変更が既存の検証根拠へ及ぼす影響を確認する。

## 失敗を次回の改善へ戻す

改善を依頼されたら、元の記録を根拠に、期待と実際の差・再現条件・影響を整理する。原因が未確定なら仮説として残す。

| 観測した不足 | 改善先の候補 |
| --- | --- |
| 背景や正本に到達できない | 知識の補完、参照や検索の導線 |
| 対象を操作・観測できない | 対象固有の到達手順、道具、検証環境 |
| 指示が曖昧・矛盾している | 依頼条件、手順、期待する挙動の例 |
| 同じ違反が繰り返される | 再現テスト、lint、権限、コード構造 |
| 製品自体が要求を満たさない | 製品の修正。検証条件を弱めて成功扱いにしない |

再利用する知識には根拠と成立条件を残し、観測事実と仮説を分ける。一度の失敗を恒久的な禁止へ一般化せず、誤りの訂正は元記録との対応を保つ。

改善は一つの原因に絞り、比較可能な課題・条件で変更前後を確かめる。通常・過去の失敗・人へ戻すケースから関係するものを使い、影響が広い変更では調整に使っていないケースも見る。完了条件の達成、再発、人の説明・確認・手直し時間、再試行を含む総費用で価値を判断する。

まず既存の一人の実行者と一件の仕事で不足を観測する。並列化・助言役・判断専用モデル・定期評価・非同期の記憶整理は、観測した不足を解消する候補として選ぶ。新しい基盤やモデル追加を最小構成の前提にせず、指定済みの構成や規模は尊重する。
