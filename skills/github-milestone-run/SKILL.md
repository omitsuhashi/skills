# GitHubマイルストーンを実装する

## 入力・出力・必要な能力

- 入力は `https://github.com/OWNER/REPO/milestone/NUMBER` またはリポジトリ名とマイルストーン番号。呼び出し例は `$github-milestone-run https://github.com/OWNER/REPO/milestone/NUMBER`。
- 出力はマージ済みPRと閉じたIssueの対応、変更が不要だったIssueの根拠、残件と再開条件。
- 対象リポジトリでの編集・検証・push、GitHubでのIssue・PR・レビュー・チェックの参照と操作、確認済みhead SHAを指定できるマージ手段が必要。利用可能なコネクター・API・CLIから能力を確認する。一覧取得に失敗した場合は再試行または代替手段で確認し、全件を確認できない場合は `BLOCKED` とする。

## 実行依頼とマージ許可

対象を指定した実行依頼には、そのマイルストーン内の実装、push、PR作成、レビュー依頼と対応、条件を満たしたPRのマージ、完了したIssueのクローズへの許可が含まれる。マージ条件が揃ったら、PRごとの再承認を求めず、その場でマージする。リポジトリが別途要求する人のレビュー承認と、利用者が依頼時に指定した制約は満たす。URLの参照や進捗確認だけの依頼では読み取りに留める。リリース・デプロイ・外部サービスへの操作には個別の許可を使う。

## 対象を確認し、Issue単位で進める

1. URLからリポジトリとマイルストーン番号を確定し、GitHubで実在を確認する。対象リポジトリの最新版の規約、既定ブランチ、承認条件を読む。マイルストーン所属のオープンIssueを全ページ取得し、PRを除く。REST APIなら `GET /repos/{owner}/{repo}/issues` に `milestone=<番号>` と `state=open` を指定し、`pull_request` キーのある項目を除く。[GitHub REST API](https://docs.github.com/en/rest/issues/issues#list-repository-issues)
2. Issue本文・関連コメント・依存関係・既存PRを確認する。依存が解消し、受入条件を確定できるIssueから進める。順序指定がなければ、着手可能なIssueを番号順で選ぶ。範囲外の依存や仕様の矛盾で止まったIssueがあっても、独立して着手できるIssueを進める。
3. 既存の適切なPRを再利用する。新規実装は最新の既定ブランチを起点に、リポジトリ規約に沿うブランチ・worktreeで行う。Issueの受入条件に沿って実装・検証し、結果をPR本文に記録する。実装が必要なIssueには原則1件のPRを用意する。分割が必要なら同じIssueに複数PRを紐づけ、各PRの担当Issueは1件にする。部分PRは `Refs #番号`、そのマージで完了条件を満たす最終PRは `Closes #番号` で結び、他のIssueを巻き込むクローズ指定がないか確認する。
4. 現行コード・既存のマージ済みPRなどで完了条件の充足を確認でき、変更が不要なら根拠を記録してIssueを閉じる。実装の要否や完了を判断できない場合はIssueを開いたまま保留する。

## レビューとCIを確認してマージする

1. PRをレビュー可能にし、GitHub上で最新headに対するCodexレビューとCIを確認する。最近のPRや設定から、対象のレビュー投稿者と完了の証拠、必要なチェックを特定する。自動レビューが開始しない場合は、利用可能なCodex連携でそのheadに対して一度だけ依頼する。GitHub連携ではPRコメントの `@codex review` を使える。[CodexのGitHubレビュー](https://learn.chatgpt.com/docs/third-party/github)
2. 実行中のレビュー・CIは同じ実行内で結果を追い、待機中に進められるIssueがあれば進める。対応すべき指摘や検証失敗を修正して再検証する。push後は新しいheadでレビューとCIを確認し直す。レビューの受付、コメントがない状態、古いheadの結果、空のチェック一覧は成功の証拠に使わない。Codexの正式なApproveがなくても、信頼できるレビュー元がそのheadについて完了を報告し、対応すべき指摘が解消していればCodexの条件を満たす。レビューの未開始・失敗・結果不明が続く場合は状態を照合し、原因を解消できなければマージを保留する。
3. マージ前に、Issueが引き続き対象であること、正しいPRとマージ先であること、受入条件・必要なCIとチェック・リポジトリ所定の承認が揃い、競合や対応すべき指摘がないことを確認する。マージがデプロイなども起動する構成では、その操作の許可も確認する。許可された方式で、確認済みhead SHAをマージ操作の期待値に渡す。直接マージならRESTの `sha` を使える。キュー経由でも、実際にマージされるheadが確認済みSHAに固定される手段を使う。条件を満たせない場合は保留する。SHA不一致で拒否されたら最新headのレビュー・CI・承認から確認し直す。[GitHubのマージAPI](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)
4. 実際のマージをGitHubで再取得して確認する。最終PRでは担当Issueのクローズも確認し、自動クローズされない場合は、受入条件を満たしたこととマージ済みPRを根拠にクローズする。途中のPRだけがマージされたIssueは残条件を進める。操作結果が不明な場合はGitHubの状態を照合してから再試行する。

## 継続と完了

各Issueの進捗後と再開時に、マイルストーンの所属、Issue・PRの状態、依存を再取得し、次のIssueへ進む。マイルストーンのオープンIssueが0件で、今回進めたPRのマージと担当Issueのクローズを確認できるまで、同じ実行でこのサイクルを繰り返す。マイルストーン自体の状態変更は、依頼された場合に行う。

未完了で止めるのは、資料やコードを照合しても解消できない不整合や疑問点など、人の判断が必要な場合か、必須承認・権限の不足や復旧できない外部障害で続行できない場合に限る。該当するIssueを保留し、進められるIssueと追跡中のレビュー・CIを処理してから、残件ごとにIssue・PRのURL、確認したhead SHA、最後のレビュー・CI結果、再開に必要な判断または操作を伝える。同じマイルストーンを再指定された場合は、最新の状態と既存PRから続ける。
